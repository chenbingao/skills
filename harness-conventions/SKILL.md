# harness 目录规范（人机协同工作区）

`harness/` 是人与 AI 协同的工作区。规范的核心是**四层分工**与**单一真相**：每类内容只有一个家，别处只引用、不复制。

## 一、四层目录

| 目录 | 装什么 | 读者 | 术语与代码 |
|---|---|---|---|
| `harness/specs/` | **业务规格，SDD 驱动开发的输入**：业务是什么、业务之间怎么交互、要达成什么效果、业务约束、待确认 | 产品 / 需求方 / 前端 / 测试 | **禁止**：整篇代码块为 0，不出现语言、框架、库、数据库对象与键名、字段类型、接口路径、错误码 |
| `harness/tech/` | **研发技术约定**：部署与迁移、架构与编码约定、开发流程与角色分工 | 研发 | 允许术语与代码片段 |
| `harness/tech/api/` | **接口字段级明细**：JSON、字段表、错误码表、请求头、分页与幂等约定 | 研发 / 前端 | 允许 |
| `harness/observe/` | **旁路观测系统**：与源代码隔离的外部集成冒烟，**用于验收** | 研发 / 验收角色 / 需求方本人 | 允许（用例是脚本） |
| `harness/.ai/` | **AI 协同过程产物**：实施计划、进度账本、各角色报告、观测运行产物 | AI 与人协作过程 | 允许；**不进版本库**（gitignore） |

判据一句话：**不懂实现的人读一遍就能确认"是不是这个意思"** → 该内容属于 `specs/`；否则它属于 `tech/` 或 `.ai/`。

## 二、单一真相（每条事实只有一个家）

| 事实 | 唯一的家 | 别处怎么处理 |
|---|---|---|
| 业务规则、业务实体与关系、交互口径 | `harness/specs/` | 只引用编号，不重复正文 |
| 建表语句、字段类型、索引、约束表达式 | 迁移文件（代码） | spec 开头点明"落地以迁移为准"，不贴 DDL |
| 请求/响应字段、错误码 | **代码生成的接口规范**（Swagger / OpenAPI 快照） | 未实现的接口写进 `tech/api/` 明细；已实现的指过去，不复制 |
| 架构分层、端口约定、覆盖率门槛、部署与迁移纪律、角色流程 | `harness/tech/` | spec 不写这些 |
| 需求原文的措辞 | 需求文档本身 | spec 照抄措辞并标章节号，不改写业务含义 |
| 过程（谁在何时改了什么、修复轮次、阶段规划） | **git 历史** | 任何文档与代码注释都不写；`harness/.ai/` 的过程产物可以记录过程，但**不得作为需求/契约/架构依据** |

## 三、依据与来源

**依据优先级**：**需求正文 > 截图 > 我们补全的推断**。

| 情形 | 处置 |
|---|---|
| 正文与截图矛盾 | 以**正文**为准，该处正文表述即为规则，并从「待确认」移出（结清） |
| 正文没写、只有截图有 | 以**截图**为准：截图是有效依据，据它写出规则并标截图编号；截图未覆盖的细节（字段清单、阈值、审批人）进待确认，不凭空补齐 |
| 我们标的【推断】与正文或截图冲突 | 以正文/截图为准，修正或删除该推断 |
| 正文自身前后矛盾 | **不许自行选一个** → 进「待确认」并标出两处出处 |

**来源标注**：每条规则括注其出处，优先级为 **原文章节号 + 截图编号** > 既有编号（`FR-*` / `API-*` / `DEC-*` / `CFG-*` / `R-*`）> 其它 spec。段落号这类抽取中间产物不要写进规格。

**【推断】标注**：需求没写、由我们补全的内容，一律就地标【推断】，并在报告里汇总成清单，便于评审逐条否决/确认。

**待确认编号**：沿用已有 `Q*` 号段；**新增项用领域前缀**（如 `Q-CLOCK-*`、`Q-FLOW-*`、`Q-CFG-*`），避免多人并行时号段冲突。问题清单**只留仍未解决**的；已结清的删掉，规则本身写进正文。

## 四、需求原文与截图基线

- **原文是唯一权威**：抽取出的 markdown/文本只是便利副本；两者不一致时以原文为准，并把差异记进报告。
- **基线要固定并留痕**：记录原文的路径、修改时间与内容摘要（如 md5），并在规格里声明依据的是哪一版。
- **截图编号按内容对齐，不套公式**：不同版本抽取的图片编号常常整体错位，且可能夹杂"旧版有、新版已删"与"新版新增"的图。做法：按**内容摘要逐张对齐**出一张映射表，并把基线原图另存一个目录，规格里一律引用**基线编号**。
- **结论必须来自逐张肉眼看图**：OCR 只能当旁证（实测会出现"图上确有、OCR 识别不出"的情况，仅凭 OCR 会得出相反结论）。看不准的图如实标注"不确定"，不要猜。
- 引用格式：`基线 imageN`；若某条规则所依赖的图在基线中已不存在，标注出来交需求方裁决，**不要硬套一个新编号**。

## 五、旁路观测系统（验收工具）

- **与源代码隔离**：不引用被测项目代码、不依赖其构建产物与测试替身；只从外部观测——对外行为经 HTTP，内部状态**直接查数据库与缓存**（旁路的意义：不依赖被测系统自报）。
- **入口单一**：一个可执行入口跑全部用例，支持列用例、按名过滤、失败即停/继续；用例按文件组织（一个用例一个可执行文件）。
- **用例契约**：退出码 0 = 通过；自建临时数据并**自行清理**（失败路径也要清）；每条断言标注它验证的 spec 编号。
- **产物落 `.ai/`**：每次运行的日志与控制台输出落 `harness/.ai/observe-out/<时间戳>/`，不进版本库。
- **验收怎么用**：验收角色独立跑它取证，不满足于转述他人报告；规格改动后应重跑以确认没把行为改坏。

## 六、过程产物（`.ai/`）

- 装：实施计划、进度账本、各角色报告、观测产物、脚本核对日志。
- **不进版本库**；新克隆的仓库没有它是正常的（流程的恢复能力因此只依赖本地）。
- 引用纪律：**任何需求、契约、架构结论都不得以 `.ai/` 下的内容为依据**——依据只能是 `specs/`、`tech/` 与代码。

## 七、协作与提交

- **提交粒度**：一个任务一个提交；提交信息用约定式（`type(scope): 中文摘要` + 条目化正文），**需经确认**；不执行推送。
- **提交前先落地自己的改动**：协调者/主控在派发"会提交的角色"之前，先把自己的改动提交掉，否则会被对方的提交扫进去（工作区纪律）。
- **一个文件的混合改动**：若同一文件同时含多方改动，提交信息必须如实说明两处，不许只写一方。
- **串行执行**：多个角色（开发 / 测试 / 验收）对同一工作区**串行**，不要并行写同一批文件；并行任务必须划分**文件所有权**。

## 八、自检清单

建立或维护 harness 工作区时逐条过：

- [ ] `specs/` 里代码块数为 0，且无实现技术名词
- [ ] 每条业务规则都括注了来源（原文/截图/编号）
- [ ] 补全内容都标了【推断】，且有清单
- [ ] 待确认项用领域前缀编号，且只留未解决的
- [ ] 建表语句、字段类型、索引只存在于迁移；字段级契约只在接口规范或 `tech/api/`
- [ ] 截图引用是**基线编号**，并有一张内容对齐表；结论来自逐张看图而非 OCR
- [ ] 观测用例不 import 被测代码；退出码语义与产物目录正确
- [ ] `.ai/` 已被忽略；没有任何结论以 `.ai/` 为依据
- [ ] 文档与代码注释里没有"谁在何时改了什么"（历史只在 git）
