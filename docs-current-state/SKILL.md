# 项目文档写作规则

两条硬规则，都不可协商：

- **甲：文档只描述当前状态**（不写历史）
- **乙：spec 是业务文档**（不堆术语、不堆代码，人能直接看懂）

## 硬规则甲：所有文档与代码注释只描述当前状态

1. 不得记录任何 AI 修改历史（谁在第几轮改了什么、原来是什么、被谁推翻、有过哪些阶段）。
2. **更新当前状态时，不得把尚未确认的实现偏差写成新的业务规则。** 实现与需求不一致时，正确做法是回到需求方确认；不得用"文档追认实现"的方式把偏差合法化。

**推论**：历史记录的唯一去处是 git 历史（提交信息、diff）。文档里不重复它。

### 禁止清单（甲）

| 禁止 | 例子 |
|---|---|
| 临时阶段规划 | 「本次开发分 phase1~phase5」「第一阶段…第二阶段…」——任何文档都不许出现这些阶段名与字段描述 |
| 被取代的旧决策 | 决策 A 曾经是现状、本次改为 B → **只写 B**。不得出现「原为 A，现改为 B」「A 已废弃」 |
| 修订记录 / 变更日志表 | 「## 修订记录」这类表整体不写（它按定义就是历史） |
| 修改者与轮次 | 「由测试角色发现并裁决」「修复轮 3 引入」「某次评审后追加」 |
| 实现过程叙述 | 「先按 X 实现，后来发现 Y」——只写最终成立的规则 |
| 未确认的偏差 | 实现里存在但需求方没确认的行为，**不得**写成"业务规则"；应列为待确认项 |
| 已解决的问题清单 | 「问题清单」里只留**仍未解决**的；已修好的条目属于历史，删掉（规则本身该写进正文） |

### 允许保留（这些不是历史）

| 保留 | 说明 |
|---|---|
| 规则成立的理由 | 「这里用 COALESCE 表达式唯一索引：该列可空，而 PG 中 NULL 互不相等，普通唯一约束会失效」——描述的是**当前为什么这样**，不是"曾经怎样" |
| 不变量与代价 | 「漏生成主键会被 NOT NULL 拦下，不会静默写错数据」 |
| 需求原文与编号引用 | `FR-AUTH-02`、`API-CLOCK-01`、`DEC-007` 等可追溯编号 |
| 文件头元信息 | 状态、上游、下游、**更新日期**（日期是元数据，不是历史叙述） |
| 待确认项 | 尚未定论的问题清单（它们描述"当前未决"，不是历史） |

## 硬规则乙：spec 是业务文档，不堆术语、不堆代码

**读者是谁**：产品 / 需求方 / 前端 / 测试。目标是一句判据——**不懂实现的人读一遍就能确认"是不是这个意思"**。

**spec 里写什么**：

1. **业务是什么**：业务实体与它们的业务定义
2. **业务之间怎么交互**：谁在什么场景下触发什么、另一方如何响应、双方约定什么
3. **要达成什么效果**：期望的业务结果、判定口径、状态如何流转
4. **业务约束**：唯一性、取值范围、先后顺序、额度与时限
5. **待确认**：仍未定论的问题

**spec 里禁止什么**：

| 禁止 | 例子 |
|---|---|
| 代码块 | 建表语句、SQL、JSON 请求/响应、YAML、配置片段、命令行 —— **整篇代码块数应为 0** |
| 实现技术名 | 编程语言、框架、库、数据库对象与内部机制、运维概念（如 `sqlx`、`Redis`、`uuid`、`BTree`、`Pod`） |
| 字段级实现细节 | 字段类型（`varchar(32)`）、索引定义、键名（`sess:{sha256(token)}`）、序列化格式 |
| 版本与内部编号 | PG 版本、迁移文件名、内部任务编号 |

**依据冲突时的优先级**：**需求正文 > 截图 > 我们补全的推断**。

| 情形 | 处置 |
|---|---|
| 正文与截图矛盾 | **以正文为准**，该处正文表述即为规则；**从「待确认」移出（结清）**，不要留着悬空 |
| 正文没写、只有截图里有 | **不算规则**：列为待确认请需求方确认，或本期不实现；不得据截图自行补出规则 |
| 我们标的【推断】与正文或截图冲突 | 以正文/截图为准，修正或删除该推断 |
| 正文自身前后矛盾 | **不许自行选一个** → 列入「待确认」并标出两处出处 |

**改写的落点**（技术内容不是被删掉，而是归位）：

| 技术内容 | 去处 |
|---|---|
| 建表语句、字段类型、索引 | 代码（迁移文件）——**唯一真相** |
| 请求/响应字段、错误码 | 由代码生成的接口规范（Swagger / OpenAPI） |
| 架构与编码约定、部署与迁移、开发流程 | `harness/tech/` |
| AI 过程产物（计划、报告、进度） | `harness/.ai/`（不进版本库） |

**改写示例**：

| ❌ 堆术语/代码 | ✅ 业务口径 |
|---|---|
| `business_date date NOT NULL`，按 Asia/Shanghai 切分 | 打卡归到哪一天，按公司所在时区（东八区）划分 |
| `clock_method clock_method[] NOT NULL` — 打卡方式集合，任一满足即可 | 一个考勤组可以同时允许多种打卡方式，员工满足任意一种即算有效打卡 |
| `CREATE UNIQUE INDEX ... ON attendance_group_members (...)` | 同一个考勤组里，同一个部门或同一个员工只能出现一次 |
| `sessions:{employee_id}:{client_type}`（ZSET，member=sha256(token)） | 每个员工每种客户端同时只保留一个登录会话 |

## 判定方法（三问）

对每一句拿不准的话，依次问：

1. **它描述的是"现在是什么"，还是"曾经怎样 / 谁改的"？** 后者删。
2. **删掉它，读者还能不能正确理解当前状态？** 能，就删。
3. **它是规则成立的理由，还是规则演变的过程？** 理由留，过程删。

再加一问（面向 spec 的读者）：

4. **一个不懂实现的人，能不能直接看懂这句话？** 不能 → 改写成业务语言，或把技术细节移出 spec。

## 适用范围与边界

- **适用**：`harness/specs/`（**业务规格，SDD 驱动开发的输入**）、项目文档、README、设计说明、交接文档、**全部代码注释**（含迁移 SQL 的注释）。
  - 代码注释的甲规则同样适用；乙规则不适用于代码与其注释（代码本就是实现，写清"现在为什么这样"即可）。
  - `harness/tech/` 是工程约定，允许技术术语与代码片段；**甲规则仍适用**（同样不写历史）。
- **规格是业务描述，不是过程记录**：它回答"这个业务现在是什么样"；任何"谁在什么时候改了什么"都不属于它。
- **边界**：`harness/.ai/` 下的协同过程产物（实施计划、进度账本、各角色报告）本身是"过程的记录"，允许记录过程；但它们**不是业务描述**，任何需求、契约、架构问题都不得以它们为依据 —— 依据只能是 `harness/specs/`、`harness/tech/` 与代码。
- 需要"当时怎么改的"，看 git：`git log -p -- <file>`。

## 自检清单

交付文档或注释前逐条过：

- [ ] 全文搜过 `原为` / `原先` / `此前` / `改为` / `废弃` / `推翻` / `不再` / `曾经`，命中处逐句判断
- [ ] 没有「修订记录」「变更日志」类章节
- [ ] 没有出现开发阶段名（phase、第 N 阶段）
- [ ] 没有出现角色名、轮次、日期化的"谁在何时改了什么"
- [ ] 没有把未确认的实现偏差写成规则（若有，改为「待确认」）
- [ ] 已解决的问题没有留在"问题清单"里
- [ ] **（spec）代码块数为 0**：`grep -c '^```' <文件>` 应为 0
- [ ] **（spec）无实现技术名词**：搜语言/框架/库/数据库对象/键名/字段类型
- [ ] **（spec）每条陈述都能被非工程读者看懂**
- [ ] 文件头的更新日期已更新
